# Notes pour les agents IA

- Monorepo pnpm. Toujours `pnpm --filter <pkg>`. Après une modif de `packages/shared`, `pnpm --filter @ygo/shared build`.
- Les schémas zod de `packages/shared` sont la source de vérité des inputs : les réutiliser côté API (`ZodValidationPipe`) et côté web. Ne pas dupliquer.
- Toute requête sur des données utilisateur filtre par `userId`. Le guard JWT est global : une route publique doit être marquée `@Public()`.
- Prisma 7 : client généré dans `apps/api/src/generated/prisma` (ignoré par git), `prisma.config.ts` porte l'URL. Nouvelle migration : `pnpm --filter @ygo/api prisma:migrate --name <nom>`.
- Next 16 : `middleware` s'appelle `proxy` (`apps/web/src/proxy.ts`). Lire `node_modules/next/dist/docs` avant d'utiliser une API Next.
- Pas de `incremental` dans le tsconfig de l'API (casse `nest build` avec `deleteOutDir`).
- Logique métier pure (règles de deck, couverture) = fonctions sans I/O + tests vitest à côté.
- Scripts CLI : dans `apps/api/src/cli/` (compilés par `nest build`). Pas de `tsx` : esbuild n'émet pas les métadonnées de décorateurs, l'injection de dépendances Nest casse.
- Moteur meta = `apps/api/src/modules/meta-decks/engine/` (pur, sans Prisma). Fixture de vraies listes dans `fixtures.ts`.
- Moteur de synergie = `apps/api/src/modules/synergy/engine/` (pur) : `parse.ts` lit les textes PSCT (anglais), `graph.ts` liens/rôles/Extra, `combos.ts` simulation, `guide.ts` guide FR. Fixtures = vrais textes Blue-Eyes. Toute nouvelle tournure de texte → un test dans `parse.test.ts`.
- L'IA des guides est optionnelle (`AI_PROVIDER`) : le guide calculé doit toujours rester complet seul.
- Interactions entre cartes : `engine/interactions.ts` (cibles + précision) → table `CardEffectTarget` (`interaction-index.service.ts`). Après une évolution du lecteur de textes, incrémenter `INTERACTION_INDEX_VERSION` : l'index est reconstruit au démarrage.
- Produits possédés = module `products` (import, `OwnedProduct`, contenu). Quantités officielles lues à la demande sur Yugipedia (`set-list.parser.ts`, testé sur de vrais extraits) → `CardPrint.setQuantity` ; inconnues → 1 par carte. Les requêtes SQL communes aux produits sont dans `common/catalog/product-sql.ts`.
- i18n : 5 langues (`APP_LOCALES` dans `packages/shared`), cookie `NEXT_LOCALE` sinon Accept-Language, anglais par défaut. Front : next-intl sans préfixe d'URL, messages dans `apps/web/messages/<locale>/<namespace>.json` (l'anglais est la référence, clé manquante → anglais). API : `t()` / `translator()` (`common/i18n`), langue de la requête via AsyncLocalStorage ; noms/effets des cartes via `nameFr/descFr` + table `CardTranslation` (de, it, pt). Tout nouveau texte visible = une clé dans les 5 langues.
- Decks officiels (structure, starters, decks de coffrets) : `ProductDeck`/`ProductDeckCard`, une section « … Deck » de la liste Yugipedia = un deck (`officialDecks()` dans `set-list.parser.ts`). Rafraîchis par `official-decks.service.ts` (cron). Catégorie du filtre : `officialDeckKind()` (plusieurs decks dans un produit = coffret).
- Auth des clients natifs (app iOS, dépôt séparé ygo-deckbuilder-iOS) : en-tête `X-Auth-Mode: token` → tokens dans le corps (`TokenSessionDto`), refresh/logout avec `{ refreshToken }` dans le corps. Le web garde les cookies httpOnly. Toute évolution d'un DTO consommé par l'app iOS → mettre à jour ses modèles (`Core/Models`).
- Simulateur de duel = module `duel` : moteur EDOPro (`ocgcore-wasm`, import dynamique ESM dans `engine/core.ts`), données ProjectIgnis téléchargées au runtime dans `DUEL_DATA_DIR` (`data/duel-data.service.ts`, jamais commitées). Pur et testé : `engine/view.ts` (repère moteur ↔ client, joueur 0 = l'utilisateur), `prompts.ts` (messages SELECT_* → invites, réponses validées, adversaire passif), `events.ts` (journal), `bot.ts` (adversaire automatique : heuristiques pures, testées avec un faux `BotWorld`, plafonds anti-boucle par tour). Pas de WebSocket : chaque réponse HTTP renvoie état + événements + prochaine invite. Contrat dans `packages/shared/src/schemas/duel.ts`. Le projet est AGPL-3.0 à cause du moteur.
- Replay du duel (web) : `use-duel.ts` fige le terrain et rejoue les événements de chaque réponse (`fx/timeline.ts` : durée, bruitage, secousse par événement ; `fx/fx-stage.tsx` : plans ; `fx/sound.ts` : bruitages Web Audio synthétisés). Même principe côté iOS (`Features/Duel/Fx`).
- Règles officielles (page `/rules`) : contenu statique `apps/web/messages/<locale>/rules.json`, lu avec `t.raw` (les tableaux ne sont pas fusionnés avec l'anglais). Une section = `{ id, group, icon, title, summary, diagram?, cards?, paragraphs, points, example? }` ; `groups` ordonne le sommaire, `diagrams` porte les étiquettes des schémas, `glossary` et `links` closent la page. Les schémas sont des SVG React (`features/rules/rule-diagram.tsx`, couleurs du thème, aucune image externe) ; `cards` liste des noms **anglais** cherchés dans le catalogue (`rule-cards.tsx`, résultat `approximate` ignoré) donc aucun code de carte n'est figé. `video` (facultatif, **français seulement** : les tutos sont en français) est lu par `rule-video.tsx`, qui pose une iframe `youtube-nocookie.com` en `loading="lazy"` (la page en compte une douzaine) ; ne jamais y mettre un identifiant de vidéo non vérifié. Toute nouvelle clé doit exister dans les 5 langues et l'app iOS lit le même JSON (`Resources/messages.<lang>.json`).
- Suivi par extension (onglet Extensions de la collection) = module `releases`. **Toutes** les extensions du catalogue y sont listées, y compris celles dont aucune carte n'est connue : le but est de les avoir toutes sous les yeux. Deux lectures de l'avancement sont toujours renvoyées ensemble — l'impression exacte (`ownedPrints`/`prints`) et la carte quelle que soit son édition (`ownedCards`/`cards`) ; l'interface choisit laquelle montrer. Les chiffres viennent de la table `SetProgress`, pas d'un agrégat à la volée (voir ci-dessous). La logique pure (statut d'une sortie, ordre des raretés) est dans `release-progress.ts`, testée. Le SQL lourd et la non-dérive de `SetProgress` sont vérifiés par `releases.integration.test.ts`, ignoré sans `INTEGRATION_DATABASE_URL` (il vide les tables de la base pointée).
- `SetProgress` (une ligne par utilisateur × extension possédée) est une dénormalisation assumée, tenue par `SetProgressService`. Deux règles la gardent juste, et les casser fait mentir l'interface : **tout** écrit sur `CollectionItem` appelle `afterCards(userId, cardIds)` (collection, import et retrait de produit, « je l'ai eue » de la wishlist), et une synchro du catalogue appelle `rebuildAll()` — de nouvelles impressions changent les totaux d'extensions auxquelles personne n'a touché. Le recalcul part des cartes possédées et couvre **toutes** les extensions qui les contiennent : « possédée toutes éditions confondues » dépend de la carte, pas de l'impression. Une ligne disparaît quand l'utilisateur n'a plus rien de l'extension.
- Sorties annoncées : `catalog-sync/upcoming-sets.service.ts` (cron quotidien) interroge l'API sémantique de Yugipedia (`action=ask`, propriétés `English release date` / `English set prefix` / `Set type`) parce que YGOPRODeck ne connaît une extension qu'une fois ses cartes révélées. Parseur testé sur une vraie réponse (`upcoming-sets.parser.ts`). Corollaire : la synchro du catalogue ne met plus à jour un set avec des champs null (`withoutNulls`), sinon elle effacerait ces dates.
- Étiquettes personnelles = module `tags` (`Tag`, `CardTag`, `SetTag`). Elles se cumulent en filtre (ET, pas OU) via `common/catalog/tag-sql.ts`, qui joint toujours `Tag` sur `userId` : on ne filtre jamais sur l'étiquette d'un autre compte. À ne pas confondre avec les **facettes** (archétype, rareté, langue, état, extension, année…), qui se déduisent du catalogue : `GET /collection/facets` et `GET /collection/releases/facets` renvoient les valeurs réellement présentes avec leur effectif, et le front n'affiche jamais un filtre qui ne renverrait rien.
- Profils et amis = module `social`. Une seule ligne `Friendship` par relation, orientée par le demandeur : **les deux sens sont donc à interroger partout**, et `friendship.ts` (pur, testé) dit l'état vu par qui regarde. Trois garde-fous vivent dans la migration parce que Prisma ne sait pas les exprimer : `Friendship_not_self`, l'index unique sur la **paire non ordonnée** (sinon A→B et B→A coexistent) et l'unicité du pseudo **sans distinction de casse** (`lower(username)`) — d'où les `mode: 'insensitive'` à l'inscription comme au renommage. Ce que voient deux amis est volontairement borné : profil, repères de collection, avancement par extension. Jamais la collection complète ; tout part de `friendIds`, et `social.integration.test.ts` tient cette frontière.
- Images de profil : disque (`UPLOADS_DIR`, à monter en volume et à sauvegarder avec la base), **réencodées en WebP par sharp**. C'est le réencodage, pas le type MIME annoncé, qui garantit que le fichier servi est une image — un SVG piégé ne survit pas au décodage, et l'EXIF d'une photo ne part pas avec l'avatar. Les chemins ont une forme fermée (`image-path.ts`, testé) et le nom porte un jeton aléatoire, ce qui permet un cache permanent et rend une image remplacée inatteignable. Le front les affiche via `/api/uploads/...` (proxy Next), jamais en URL absolue.
- Cartes mises en avant (`ProfileCard`) : des **impressions**, et la possession est vérifiée à l'écriture ET à la lecture — une carte vendue disparaît du profil sans nettoyage.
- Type de produit `BOOSTER` : un booster principal ne porte presque jamais le mot « pack » dans son nom, donc `PRODUCT_KIND` se rabat sur `cardCount >= 50` après avoir attrapé les familles nommées. Toute évolution de cette heuristique change le filtre par type des trois onglets.
